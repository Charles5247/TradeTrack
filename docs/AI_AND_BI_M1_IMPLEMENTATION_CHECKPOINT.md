## Merchant workflow

When enabled, Inventory → Receive stock opens `/inventory/intake`. A manager chooses opening stock or an additional delivery, a location and catalog products. Each line records the original purchase quantity/unit, explicitly confirmed whole-unit conversion and purchase cost. Costs start blank. The review shows every prepared line, the purchase total, current stock snapshot and expected increments. A single approval saves the receipt atomically; saved status, outcomes and retries remain available in the paginated receipt list.

New products are explicit reviewed drafts with separate catalog cost/selling price fields. Repeated lines can share one draft within the receipt and create one product. Existing catalog prices are preserved. A repeated supplier/invoice fingerprint requires a reviewed acknowledgment reason before it can post. Source text, quantities, conversions, corrections and every server-prepared revision remain recorded. Opening stock requires no existing inventory position or movement history at that product/location.

Small drafts use tenant/account-specific local storage. Preparing a server review and posting require connectivity. Changing accounts hides the previous account's draft and receipts. Opening history asks before replacing edited local work. Failed or interrupted requests retain their receipt ID; reconnect, open the saved receipt and inspect authoritative status before retrying. A response lost after commit does not create another stock effect.

## Engineering contract

- `20261021024854_m1_manual_stock_receipts.sql`: receipt headers/lines, immutable revisions and approvals, manager/tenant RLS and restricted grants. `save_stock_intake` enforces expected revisions and creates a reviewed payload hash. Editing clears the current approval while preserving its historical record.
- `approve_stock_intake` binds actor, receipt revision and canonical payload hash. `post_stock_intake` consumes that recorded approval, rechecks the active manager and business entitlement, locks current stock, checks product identity/currency and posts all product/stock/evidence changes or none. Concurrent quantity changes alone do not invalidate an approved delivery. New-product identifier conflicts return for review.
- The authoritative inventory trigger creates signed ledger movements and audit attribution; requested movement rows are not inserted a second time. Receipt costs and original purchase units are persisted separately from catalog prices.
- `/api/stock-intakes`: authenticated GET by ID or bounded paginated history; bounded JSON POST for save/approve/post actions. Unposted receipt reads include counted, bounded current-stock queries; incomplete or failed snapshots return an explicit unavailable state without hiding receipt history or inventing zero. `/api/stock-intakes/catalog`: paginated product search and verified complete location coverage. Products beyond the first page remain selectable. The API validates input and origin; the database repeats authorization and mutation validation, including typed JSON values. Legacy PostgreSQL UUIDs are accepted and command identifiers are canonicalized before shared-draft comparisons.
- `src/lib/stock-intake/`: shared input contracts, request/error handling and tests. `src/components/inventory/manual-stock-intake.tsx`: entry, review, approval, outcomes and recovery using existing Retail components. Account revision checks reject late responses from a previous session.

Initial manual boundary: 1–1,000 lines per receipt, 2 MiB command, positive integer purchase quantities/conversions/resulting stock units, and two-decimal purchase/catalog prices within the existing numeric range. These are explicit implementation limits, not measured bulk capacity. M2 owns complete-sheet/batch uploads, durable jobs and shared drafts across multiple receipts. A future worker adapter must consume this recorded approval and preserve its verified actor; it must not impersonate a client-supplied user.
