# Track Kasuwa AI assistant: codebase map and proposed batches

Review document, 30 October 2026. Repository baseline: `0ff05ea8edb8cbd53f624c6a6fcbd4774e25ceae`, plus the supplied working-tree spec. The full [product spec](track-kasuwa-ai-assistant-spec.md) was read, including sections 1–15. No feature code, schema, configuration, or business data was changed for this assessment.

**Evidence labels:** **Implemented** means present in inspected source, not confirmed deployed. **Gap** means absent from the inspected implementation paths. **Proposed** means a design for review. **Unknown** means this inspection cannot establish the answer. This was static inspection: no application, provider, database, browser, or native-shell acceptance tests were run. Deployed migrations, grants, configuration, real merchant data, extraction quality, Hausa fluency, costs, and platform parity remain **unknown**.

The main finding is that a text/CSV/XLSX assistant, an audited import mechanism, and limited business analysis already exist. They do not yet deliver the invoice, receiving, pricing, resumability, and contextual analytics described by sections 6–10. Inventory writes are split between browser mutations, queued snapshots, import RPCs, and a separate medical workflow; there is no single general stock-commit operation to attach an assistant to. Sources: [assistant UI](../src/app/(dashboard)/assistant/page.tsx), [AI API](../src/app/api/ai/route.ts), [import executor](../src/lib/imports/execute.ts), [inventory adjustment](../src/app/(dashboard)/inventory/page.tsx), [medical API](../src/app/api/medical-stock/route.ts).

**1. Existing write capabilities**

Common controls and limits:

- **Implemented:** `apiContext()` obtains the authenticated user, requires an active profile and organization, and defaults to Business Owner/Admin. Browser pages use `AccessGuard`; that is a UI boundary, while database policies/RPC checks provide server enforcement. `is_admin_or_above()` also includes Platform Owner, whereas the AI API and its RPC access check exclude that role. Operational RLS still requires the user's own organization. Sources: [API context](../src/lib/auth/api-context.ts), [page guard](../src/components/shared/access-guard.tsx), [role helpers](../supabase/migrations/008_role_model_rework.sql), [AI access](../supabase/migrations/016_ai_assistant_plumbing.sql).
- **Implemented:** subscription write triggers cover products, inventory, movements, transfers, sales, vendor records, POs, and import records. Thus UI fail-open plan lookups are not evidence of unrestricted database writes. **Unknown:** actual deployed trigger/grant state, and whether every subscription feature is enforced server-side; the generic subscription guard is not itself a PO-feature authorization check. Sources: [subscription guards](../supabase/migrations/20261019141921_trial_read_only_access.sql), [PO UI plan check](../src/components/purchase-orders/purchase-orders-screen.tsx), [explicit API grants](../supabase/migrations/019_explicit_api_grants.sql).
- **Implemented:** application audit rows are append-only, sequenced and hash-chained per organization; the database records the authenticated actor, role and server time. This is application/database-trigger immutability, not protection against a privileged database administrator disabling controls. Source: [audit controls](../supabase/migrations/014_accounting_controls.sql).
- **Implemented:** inventory changes generate a canonical delta movement with `reference_type='inventory_ledger'`. Several clients additionally write descriptive movement rows. Analytics must distinguish those to avoid double-counting. Sources: [stock ledger trigger](../supabase/migrations/014_accounting_controls.sql), [adjustment helper](../src/lib/inventory/adjust-stock.ts), [PO receipt](../src/components/purchase-orders/purchase-orders-screen.tsx), [accounting movement filter](../src/app/api/accounting/route.ts).

**2. Existing AI implementation and coverage of sections 6–10**

**Implemented request lifecycle:** `/assistant` accepts pasted text or a CSV/XLSX parsed in the browser. It calls `/api/ai` to reserve a job, invoke the provider and store a ready/failed result. Inventory output goes through `ImportWorkbench`; Confirm first calls AI approval with a generated batch UUID, then executes the standard import. Insight generation is read-only; delivery/preferences require explicit confirmation. Sources: [assistant UI](../src/app/(dashboard)/assistant/page.tsx), [AI route](../src/app/api/ai/route.ts), [workbench](../src/components/imports/import-workbench.tsx).

**3. Offline conflict resolution for a human-approved proposal**

**Implemented rule:** trust the executable sync engine over the older architecture prose. Generic UPDATE fetches server `updated_at`; a strictly newer server timestamp makes the local write return success without being applied. Equal timestamps proceed, despite the comment describing strictly newer client time. Timestamp comparison preserves fractional precision; this is a read-then-write, not atomic compare-and-set. Sales/items, PO/vendor creation use insert-ignore-duplicate by ID; append-only-table UPDATE is ignored. Source: [sync engine](../src/lib/offline/sync-engine.ts). The older [offline document](OFFLINE_ARCHITECTURE.md) describes a different store shape/order and does not fully describe today's branches.

**Concrete consequence:** if a merchant approves “add 12 Power Oil” while cached stock is 20, a generic snapshot would queue quantity 32. If server stock becomes 18 with a later timestamp, the queued 32 is silently superseded. The approval occurred, but +12 did not. If the local clock wins, 32 can overwrite a newer business balance derived from 18 rather than add 12. Separately queued movement/audit INSERTs can still be processed. This is an inference directly from the separate adjustment queue entries and generic LWW logic, not a reproduced incident. Sources: [adjustment queueing](../src/lib/inventory/adjust-stock.ts), [inventory-page queueing](../src/app/(dashboard)/inventory/page.tsx), [sync engine](../src/lib/offline/sync-engine.ts).

**Existing exceptions:** import commands execute `apply_import_row` and re-evaluate duplicates on the server; they do not take the generic timestamp branch. Vendor stock opts into exact `updated_at` matching and retains a “needs check” state on conflict/unknown outcome. PO lifecycle is online-only. Current AI approval calls the server immediately; that call prevents the AI-backed workbench from continuing offline, even though ordinary product imports can queue. Sources: [sync engine](../src/lib/offline/sync-engine.ts), [import executor](../src/lib/imports/execute.ts), [vendor persistence](../src/lib/offline/vendor-transactions.ts), [PO guards](../src/lib/offline/purchase-orders.ts), [AI approval callback](../src/app/(dashboard)/assistant/page.tsx).

**Proposed interpretation of the spec:** offline approval records a durable **approval intent**, never a claim of server commitment. Queue the approved revision, actor/org, expected versions and stable command ID atomically. On reconnect, reauthenticate and recheck role, organization, subscription and referenced records; server applies an attributable delta/price decision once or returns a visible conflict. Material changes to product identity/unit/current price/PO outstanding quantity require re-review. Do not silently translate an approved intent into a different command or relabel a dropped snapshot “applied.” Preserve the existing generic rule for existing manual flows, but explicitly approve this command-specific conflict policy before shipping AI stock approval. This proposal follows [spec sections 3 and 6.10](track-kasuwa-ai-assistant-spec.md), using the existing [vendor version-check pattern](../src/lib/offline/sync-engine.ts) and [idempotent import pattern](../supabase/migrations/015_business_imports.sql).

**4. Proposed draft/commit design**

This section is a proposal, not an implemented schema or authorization decision. It builds on [AI jobs](../supabase/migrations/016_ai_assistant_plumbing.sql), [immutable import results](../supabase/migrations/015_business_imports.sql), [medical request replay](../supabase/migrations/20261020183746_medical_batch_inventory.sql), and [audit correlation](../supabase/migrations/014_accounting_controls.sql).

1. **Draft storage:** retain `ai_jobs` as generation attempts; add org-scoped proposal/revision/row records rather than treating the mutable `result` JSON as the whole approval contract. Store source fingerprint, uploader, generation/model/prompt version, locale, extraction evidence, uncertainty, normalized quantity/unit, target IDs and expected versions. Raw document bytes belong in private org-scoped storage with a retention policy, not public product-image storage or an unlimited audit JSON. Locally persist source/upload intent, ready revision and approval outbox in org-and-user-scoped IndexedDB. The existing UI keeps proposals only in React state and has no job-list/resume API; private AI-document storage and retention are **gaps**. Sources: [assistant state](../src/app/(dashboard)/assistant/page.tsx), [AI tables](../supabase/migrations/016_ai_assistant_plumbing.sql), [offline DB](../src/lib/offline/db.ts).
2. **Review contract:** a revision distinguishes source cost, current selling price and proposed selling price. Human edits create a new revision/diff. Approve selected rows and price changes explicitly; missing costs stay unknown until resolved or explicitly permitted as unknown. Bind approval to the exact normalized command hash, revision, selected rows, actor and timestamp. Re-editing invalidates approval. This closes the current unbound batch UUID and blank-to-zero behavior. Sources: [spec 6.4–6.10](track-kasuwa-ai-assistant-spec.md), [current approval function](../supabase/migrations/016_ai_assistant_plumbing.sql), [import coercions](../supabase/migrations/015_business_imports.sql).
3. **Approval authority:** initially use current owner/admin rules; no cashier upload and no Platform Owner read until those spec questions are decided. A later cashier-to-manager handoff needs organization-visible review authorization, because current jobs are private to their requesting user and approval RPC requires that same user. Server derives all identity/org fields; client IDs are assertions to validate, not authority. Sources: [spec 14](track-kasuwa-ai-assistant-spec.md), [API context](../src/lib/auth/api-context.ts), [AI RLS/approval](../supabase/migrations/016_ai_assistant_plumbing.sql).
4. **Commit boundary:** one authenticated application/DB command validates the approved revision and executes permitted domain actions. Reuse hardened domain rules for human and AI operations; do not call an LLM to calculate totals or authorize writes. Lock affected stock/PO rows, check ownership of every relationship, and commit stock/catalog changes plus result/audit in the same database transaction. Separate generation from mutation. Suggested initial semantics: one row/action group atomic, explicit per-row batch outcomes, matching existing import result handling; multi-line PO receipt should be one atomic receipt. All-or-nothing versus per-row is still a team decision. Sources: [spec 3, 6.10 and 14](track-kasuwa-ai-assistant-spec.md), [current row transaction/results](../supabase/migrations/015_business_imports.sql), [nontransactional PO receipt](../src/components/purchase-orders/purchase-orders-screen.tsx).
5. **Replay:** stable command key per proposal revision/action; same key and payload returns the original result, changed payload is rejected. Keep upload fingerprint deduplication separate from commit idempotency; two legitimate similar invoices must not be collapsed. Current batch+row replay is useful but each UI Confirm generates a new batch, so it is not document-level deduplication. Sources: [workbench](../src/components/imports/import-workbench.tsx), [import row key](../supabase/migrations/015_business_imports.sql), [medical replay](../supabase/migrations/20261020183746_medical_batch_inventory.sql).
6. **Immutable history:** append linked events for upload, proposal revision, human edits, approval intent, accepted approval, commit outcome, conflict and reversal. Mutation audit records include `origin=ai_proposed`, proposal/revision/command IDs, approved payload hash, uploader/proposer context and approving human. Reuse audit `correlation_id` across approval and actual mutations. Preserve original model output and final reviewed values without pretending the model is the authenticated actor. Current audit infrastructure already stores before/after, actor, role, server/device times and hashes; current `AI_APPROVAL` lacks the reviewed-value binding. Sources: [audit SQL](../supabase/migrations/014_accounting_controls.sql), [AI audit functions](../supabase/migrations/016_ai_assistant_plumbing.sql), [import source preservation](../supabase/migrations/20261028122400_import_source_audit.sql).
7. **Result/reversal:** show committed/skipped/failed/conflicted/unknown outcomes with audit links. A timeout is “confirmation pending” until queried with the same key. Corrections are new adjustments/reversals; never edit the old approval/audit. Existing `reverse_import` has consumed-stock and changed-record guards; receipt-specific reversal still needs its own business design. Sources: [spec 6.10–6.11](track-kasuwa-ai-assistant-spec.md), [import reversal](../supabase/migrations/015_business_imports.sql), [medical retry UI](../src/components/medical/stock-workspace.tsx).
