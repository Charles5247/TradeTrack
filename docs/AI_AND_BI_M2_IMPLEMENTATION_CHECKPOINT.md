## Implementation contract

- Reuse M1's validated receipt command, original approving actor, immutable hashes and receipt-atomic stock changes. Public manual entry retains its 1,000-line limit; trusted batch preparation must support a complete receipt beyond 1,000 rows without treating checkpoints as receipts.
- Private CSV/XLSX originals use authorized, immutable upload sessions. Verify actual bytes/hash before preparation. Enforce 100 files, 250 MiB/batch, 20 MiB/file and 20,000 active prepared rows. Keep proposed limits distinct from measured capacity. Retention/hosting remain production requirements.
- A separate Node worker consumes PostgreSQL jobs. Claims use leases, fencing, heartbeat, at most three automatic attempts, backoff and caps of two jobs/tenant and four globally. Parser work runs in a bounded child process, so it cannot block heartbeats. Persist row checkpoints; browser closure must not stop accepted jobs.
- Inspect all worksheet names. The merchant selects sheets, header rows and deterministic column mappings. Parse every selected nonblank data row, retaining source/sheet/physical row and original cells. Preserve repeated headers and unknown values as review exceptions. No missing cost becomes zero. Existing non-intake imports retain their behavior.
- Match exact catalog identifiers without resolving conflicting SKU/barcode pairs automatically. Shared new-product drafts belong to the batch and require explicit identity/price confirmation. Repeated appearances across receipts resolve only to that batch's previously committed, unchanged reviewed product.
- Every prepared row remains available in paginated review. Corrections apply to explicitly selected rows. Grouping and receipt locations are editable before approval. A single approval freezes selected ready receipt hashes and an explicit exclusions summary. Post each receipt separately; return saved/failed/needs-review results and retry only unposted work.
- Background posting derives actor and payload from recorded approval, never caller-supplied identity. A private transaction context permits the shared command to consume trusted batch provenance/capacity. Recheck active permissions, entitlement, unit/variant identity and opening-stock history. Preserve medical batch separation.
- Cancellation stops unstarted work and preserves committed receipts and evidence. Row/source edits invalidate affected preparation and approval. Offline storage retains only small account-scoped batch references; reconnect retrieves authoritative server state.

## Delivered workflow

Inventory → Spreadsheet batch (`/inventory/intake/batches`) creates a server batch, accepts immutable private CSV/XLSX uploads and inspects all worksheets. The merchant selects complete sheets, physical headers and column mappings. A dedicated worker verifies the actual bytes/hash and prepares bounded durable checkpoints. The browser shows progress, original downloads, source previews clearly labeled as previews, all prepared rows in 100-row pages, exception queues, shared product drafts, explicit conversions and editable receipt grouping/locations. Bulk edits apply only to explicitly selected row IDs, including selections across pages. Forms retain their opening revision; concurrent changes require a refresh. A shared product identity or stock-unit change clears its appearances’ pack confirmations.

Preparing reviewed groups creates canonical M1 receipt payloads and hashes. A single merchant approval records selected ready receipts and the acknowledged exclusions summary. Each receipt posts atomically through the shared command. Partial outcomes preserve saved receipts; failed identity checks require renewed preparation/approval. Shared new drafts create one product across receipts only when its reviewed identity/prices remain unchanged. Posted rows, source evidence and approval history stay inspectable. Manual history excludes large batch payloads and directs batch receipts to this workspace.

The CLI-created migration is `20261024131715_m2_spreadsheet_batch_intake.sql`, ordered after the foundation migration. Public writes use `stock_intake_batch_command`; reads use `read_stock_intake_batch`; only the server worker can invoke `stock_intake_job_command`. Direct table writes and forged manual approvals of batch receipts are denied. Sources remain private, tenant-scoped and immutable. Restrictive bucket fences preserve that boundary even alongside an older broad permissive storage policy; anonymous rules do not require access to private intake tables. Upload sessions expire after two hours. Cancellation does not revoke an already issued provider token instantly; it stops uncommitted processing and retains evidence.

The Node worker runs from `npm run worker:stock-intake`, uses 120-second leases, ten-second heartbeats, fencing and three total automatic attempts with backoff. SQL enforces two active jobs per tenant and four globally across replicas. One process executes one job at a time; four simultaneous extractions require enough approved replicas/resources. Parser children have a 384 MiB heap and 45 seconds of active parser time; checkpoint I/O is excluded from that CPU deadline. A worker restart recovers expired leases and reuses checkpoints. Actual bytes/hash are verified before extraction. Missing uploads wait without consuming extraction retries.

Only the two bulk command functions request a 55-second database timeout; ordinary role/global settings remain unchanged. This fits inside the documented 60-second client API ceiling. Network, pool, throttling and database timeout failures remain transient. Hosted timeout configuration and runtimes must be verified before enabling the proposed maximum. See [Supabase timeout behavior](https://supabase.com/docs/guides/database/postgres/timeouts).

Node ZIP validation uses capped native decompression; the existing browser validation path remains in place. Additional explicit parser limits are 200 columns, 16 KiB of evidence per row, 64 MiB expanded XLSX archive and a 4 MiB command body. Unsupported inputs fail visibly rather than becoming incomplete accepted sources. Missing numbers/costs stay unknown; explicit zero costs remain zero.

- Confirm historical credential revocation/rotation, hosted grants/RLS/session parity, compatible-client stock rollout, approved worker hosting/budget, storage retention/recovery and representative-device/capacity results before production enablement. Credential disposition is still unknown; no key was printed or rotated.

The 20 MiB/file boundary and parser overflow tests are separate evidence. Measure hosted resource peaks, gateway/function timeouts and full-batch throughput before advertising capacity.
- Small account-scoped local references restore a server batch; originals are not retained offline. Upload, review writes and posting require connectivity. Reconnection fetches authoritative status. AI usage reservations, extraction budgets and modalities begin in later milestones; M2 does not use an AI provider.
